# Skola Phases 16 to 24: roadmap

> **For agentic workers:** this is the order of work, not a task list. Each milestone gets its own detailed plan, written (with `superpowers:writing-plans`) when the milestone starts, so the plan is checked against the code of that day. Only Milestone 1 has a detailed plan now: `2026-11-07-phase-16-1.md`.

**Goal:** build the owner-approved designs for Phases 16 to 24 in an order that keeps each step shippable and testable.

**Architecture:** every step reuses the existing review path (`updateCardModel`, `useLearning`), existing sync (whole rows, settings as keyed rows) and the pure-module pattern (logic with no Dexie or React under `src/logic/`, shared with the MCP server). Server changes are small migrations on `mcp_study_sessions` only.

**Tech Stack:** Next.js 16 (webpack), React 19, Dexie, Supabase Postgres relay, ts-fsrs, Vitest (jsdom, fake-indexeddb, PGlite), Biome.

**Specs:** `docs/spec-phase-16.md`, `docs/spec-phases-17-20.md`, `docs/spec-targeted-review.md`, `docs/spec-master-card.md`, `docs/spec-ask-ai.md`; order from `docs/SPEC.md` section 12; ADRs 0016 to 0018 (proposed).

## Global Constraints

- No cron, polling or background worker (SPEC N3).
- Local-first: UI reads and writes Dexie only; the server is a sync relay.
- FSRS: only `due` and `scheduled_days` may be changed by policy; never stability or difficulty (ADR 0006, `adr/0006-fsrs-overlay-policy.md`).
- Settings are keyed rows: add each new key to `SettingsValues` and `defaultSettings` (`src/logic/settings/`); there is no server whitelist for setting names.
- Server migrations: timestamp-named file in `supabase/migrations/`, `IF NOT EXISTS`, row security enabled, `text` ids, `bigint` millisecond timestamps; apply before deploying the code that uses them; add to every test that loads an explicit migration list.
- MCP errors keep the `[code] message` form.
- Every new setting or mode gets an `InfoTip`; every new page gets a tour entry; user-facing text goes through `t()`.
- Every step: failing test first; then `pnpm exec biome check --write`, `pnpm lint:type`, `pnpm test`; `pnpm build` for route or config changes; a browser check for UI.
- **Verify first:** before writing code for a step, re-check every file, function and field the spec names for that step (a grep and a read each); if reality differs, fix the spec text in the same change.
- Skill text is seeded only into an empty database (`adr/0006-skills-in-postgres-served-over-mcp.md`): after each skill change, update the live skill and check `get_skill`.
- Commit and push only when the owner asks.

## Review Focus

- A learner far from UTC (for example UTC+13) studying near local midnight: "today" must be the learner's day on the server and in the app.
- An MCP session on a parent deck whose sub-decks have different daily budgets and one paused sub-deck.
- An older client saving a master note written by a newer one (new fields must survive).
- Two devices writing the same setting or card row at once (last write wins; nothing may crash or double-count).
- A feature working offline in the app but its MCP twin missing (or the reverse): each part needs both.

## Rules for moving between milestones

1. A milestone is finished only when its tests, lint, typecheck and build are green, its browser checks are done, its docs (features, gotchas, HANDOFF, SPEC row, ADR status) are updated, and its skill changes are delivered and verified with `get_skill`.
2. The owner confirms before the next milestone starts and before anything is committed, pushed or deployed.
3. A migration is applied to the live database before the code that needs it ships.
